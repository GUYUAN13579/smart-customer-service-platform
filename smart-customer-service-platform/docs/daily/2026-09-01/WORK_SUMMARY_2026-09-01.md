# 2026-09-01 工作总结

## 今日完成内容

### 1. 完成 SLA 告警兜底恢复任务

新增并完成 `recoverStaleAlerts`，用于处理 RabbitMQ 异常、应用重启或消费链路中断后，长期没有结束的 SLA 告警。

处理规则：

- 查询已到计划时间、且长时间未更新的 `PENDING` 告警。
- 查询长时间停留在 `PROCESSING` 的告警。
- `PENDING` 告警保持原状态，更新错误说明和更新时间后重新投递。
- `PROCESSING` 告警先恢复为 `PENDING`，再重新投递。
- 更新时同时限定原状态、计划时间或更新时间，避免多个定时任务实例重复领取同一条记录。
- 消息重投递放在事务 `afterCommit()` 中执行，保证消费者读取时数据库状态已经提交。
- 重投递失败时，将告警更新为 `FAILED` 并记录失败原因。

本次恢复结果通过 `SlaAlertRecoveryVO` 返回：

- 本次扫描开始和结束时间。
- 恢复的 `PENDING` 数量。
- 恢复的 `PROCESSING` 数量。
- 成功重新投递的消息数量。

相关代码：

- `SlaAlertRecoveryServiceImpl`
- `SlaAlertRecoveryService`
- `SlaAlertRecoveryScheduler`
- `SlaAlertRecoveryController`
- `SlaAlertRecoveryProperties`

### 2. 补齐 SLA 告警恢复配置与手动触发入口

已在 `application-local.yml` 配置告警兜底任务参数：

```yaml
app:
  sla:
    alert-recovery:
      fixed-delay-ms: 60000
      pending-grace-minutes: 5
      processing-timeout-minutes: 10
      batch-size: 100
```

新增手动触发接口：

```http
POST /api/v1/sla/alerts/recovery/scan
```

该接口用于管理员在排查 MQ 或告警状态异常时立即执行一次扫描。对应权限 SQL：

- `docs/sql/sla_alert_recovery_permission_patch.sql`

### 3. 明确 SLA 模块当前完成度

当前 SLA 已形成如下闭环：

```text
配置 SLA 策略
-> 应用到工单并计算截止时间
-> 创建 4 条 sla_alert
-> 事务提交后投递 RabbitMQ 延迟消息
-> TTL 到期后进入正常消费队列
-> 消费者校验工单当前状态
-> 创建通知和工单操作日志
-> 告警进入 SENT / SKIPPED / FAILED
-> 失败告警可人工重试
-> 长期 PENDING / PROCESSING 告警由定时任务恢复
```
